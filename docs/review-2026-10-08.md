## 2. Critical

### B1 · Micrograms are stored as grams
> **Fixed** in `d32ca5c`. The rows it already corrupted are repaired by SQL you run — §10.


`_unmath()` in `ocr/pipeline.py` removes LaTeX from table cells. Its `_TEX_CMD` pattern deletes
`\mu` alongside formatting commands like `\mathrm` — but `\mu` isn't formatting, it's the symbol µ.

| Printed | Stored |
|---|---|
| `86 $\mu g/dL$` | Iron **86 g/dL** |
| `352 $\mu g/dL$` | TIBC **352 g/dL** |
| `284000 / $\mu L$` | Plt Count **284000 / L** |

- **Measured:** 31 occurrences across 15 documents in the cached engine output, and the corrupted
  units confirmed in `lab.results`.
- **Impact:** a factor of 10⁶. 86 g/dL of iron is lethal; 284,000 platelets per *litre* reads as
  catastrophic thrombocytopenia. The real values are normal.
- **Why 190 tests missed it:** `test_latex_in_cells.py` asserts that no TeX *survives*. Deleting µ
  satisfies that perfectly — it tests that the markup is gone, not that the meaning survived.
- **Fix:** map `\mu` → `µ` (and `\times` → `×`) before stripping; add a test asserting `µg/dL`
  survives. Then **re-extract the 15 affected documents** from `bench/results/` — free, no OCR —
  and decide what to do about any already verified.
- **Effort:** small code change; the data clean-up is the real decision.

### B2 · "Verified" mostly means "bulk-confirmed", with no quality gate
> **Gated** in `a72f471`, option (a). How useful the gate can be depends on B26 — §10.


`POST /review/confirm-all` verifies every `parsed` document whose UHID matched a patient. That is
its only criterion. It never checks whether values were read, core analytes are missing, or
mappings are unconfirmed — and `parsed` is assigned on the UHID match alone.

| Verified documents | 288 |
|---|---|
| …verified in bulk, not individually | **282 (98%)** |
| …with **no values read at all** | **35** |
| …with printed rows we failed to read | 83 |
| Unread rows now counted as clinical fact | 306 |

- **Example:** P23-R05 is *Verified*, showing LFT `0/12` and "11 core missing". Its values —
  `TOTAL BILIRUBIN0.78`, `ALT 38`, `PROTEIN, TOTAL7.3` — are glued into the label cells (B16).
  They will never reach the patient's trend.
- **Impact:** the governing rule is bypassed in practice. To be fair, this is demo data and someone
  pressed the button deliberately — the problem is that nothing stops it.
- **Options for discussion:** (a) `confirm-all` skips documents with any core-missing, no-value or
  confirm-pending row; (b) it only confirms documents at full coverage; (c) remove it and keep
  per-document review. (a) is the smallest change that keeps the time-saver.
- **Also:** re-queue the 35 empty verified documents for review.

## 3. High

### B3 · The trend chart plots undated readings in 1970
> **Fixed** in `8e67fcb` — §10.

`web/components/TrendChart.tsx:17` filters points with no value but not points with no date; line
26 does `new Date(p.collected_at)`, and `new Date(null)` is 1 January 1970. The axis then gets a
tick for every year from 1970 to 2026.
- **Seen in the browser:** a fake 1970 point, a 50-year diagonal line, five real years crushed into
  the right tenth of the chart, and an x-axis reading `1919191919…`.
- **Pinned:** `e2e/test_console.py::test_the_trend_axis_starts_at_the_first_real_reading` (xfail).
- **Fix:** filter `p.collected_at !== null` too — which `TrendPoint`'s own docstring says was the
  intent. One condition.

### B4 · An analyte appears once per panel it was printed under
> **Fixed** in `441c50a` — §10.

`GET /patients/{id}/analytes` groups by `v.panel_code` — the panel of the *section*, not the
analyte. One analyte splits into a row per panel-or-none.
- **Measured:** patient 14 gets 83 rows for 67 analytes. Haemoglobin appears as `8` (no panel) and
  `3` (CBC) — 11 readings shown as two partial series.
- **Seen in the browser:** both Haemoglobin chips selected at once; React logs a duplicate-key
  warning 48 times; the stat card says **83 chartable tests**, not 67; "most readings first"
  ranks 11 haemoglobin readings as 8.
- **Pinned:** two xfail tests in `e2e/test_console.py`.
- **Fix:** group by analyte only. One line of SQL.

### B5 · `fn_fail_document` reverts documents that were read successfully
> **Fixed** in `4034968`. Migration `030` is yours to apply — §10.

`fn_complete_document` correctly locks and refuses anything not awaiting extraction.
`fn_fail_document` has **no status guard** — it sets `received` or `failed` whatever the state.
- **Proven** by dry run in a rolled-back transaction: document 6569, `parsed` with 12 results →
  `fn_fail_document` → `received`, results still attached.
- **Two triggers.** The stale-claim race: a worker slower than 15 minutes loses its claim, fails
  to complete, and its error path reverts the winner's work. And more simply: `ocr_worker.py`
  commits the completion at line 238, then runs a `SELECT` and a `print` *inside the same try*.
  A database hiccup there calls `fn_fail_document` on the document it just completed.
- **Impact:** the document is re-read (another OCR charge) and gains a second report on top of
  the first, or is marked failed with its results still attached.
- **Fix:** guard `WHERE status IN ('received', 'parsing')` in a new migration; move the
  post-commit lines out of the try.

### B6 · Authentication fails open
> **Fixed** in `e27338d` — §10.

Auth is off whenever `ENVIRONMENT` is `development` — and `ENVIRONMENT` **defaults to**
`development`. A deployment that forgets one variable runs with no authentication.
- **Proven:** `GET /patients` with no token returns 200 with patient data.
- **Credit:** the code is careful that `practice_id` still never comes from the client.
- **Fix:** default to production; require `ENVIRONMENT=development` explicitly to disable auth.

### B7 · Errors the browser cannot read
> **Fixed** in `b3caa1d` — §10.

Only `ValueError` has an exception handler.
- An **unhandled** exception goes out as a 500 *without CORS headers* — Starlette's error
  middleware sits outside the CORS middleware — so the console sees only "Failed to fetch".
  Proven: a review of a non-existent document returns `500`, no `access-control-allow-origin`.
- That review should be a **404**. SQL functions raise, and only `patients.create` maps SQLSTATEs.
- The `ValueError` → 400 handler is too broad: any internal `ValueError` is reported as the
  client's mistake, with the internal message as the body.
- **Fix:** one catch-all handler returning a JSON envelope `{code, message, correlation_id}` with
  CORS; map the functions' RAISE codes to 404/409/422 in one place.

### B8 · `/health` leaks database errors to anyone
> **Fixed** in `b3caa1d` — §10.

It returns `f"database unreachable: {exc}"` on an unauthenticated endpoint. A psycopg connection
error carries host, port and username — sometimes "password authentication failed for user
labidp". **Fix:** generic message out, details to the log.

### B9 · Patient identifiers in the logs
> **Fixed** in `b3caa1d` — §10.

- The worker prints each document's **UHID and original filename**. Real filenames are often the
  patient's name — `bench/results/` already holds one named after its patient.
- Uvicorn's access log records search terms: `GET /patients?q=Aadhya` — confirmed in the live log.
- **Impact:** PHI in container logs, then in log aggregation, retained by whatever policy applies
  there. A DPDPA question at EMR scale.
- **Fix:** log document ids only; move patient search to a POST body or strip query strings from
  the access log.

## 8. What's missing for the EMR

Ranked by when each starts to hurt at 10k–100k documents a month.

### Before the first integration call
- **A versioned contract.** No `/v1`. The EMR needs a stable, published OpenAPI with contract tests.
- **One error envelope** with a correlation id (B7). An integrator can't handle errors it can't parse.
  *Partly done:* a 500 now carries a reference id and every error is JSON with CORS; 4xx keep
  FastAPI's `{detail}`. A versioned envelope belongs to the contract work above.
- **EMR-issued tokens.** Auth is a POC with a shared HS256 secret. The plan to swap only
  `decode_token()` is sound; add asymmetric verification (RS256/JWKS) and service-to-service
  credentials for the EMR's backend.
- ~~**Auth fail-closed** (B6) and **no default secret** (B14).~~ **Done** — `e27338d`.
- **Callbacks, not polling.** Nothing tells the EMR when a document is parsed or verified. A
  webhook with retries, or an outbox table the EMR reads.
- **Idempotent upload.** Checksum dedupe is good; the retry race (B12) returns a 500. Accept an
  `Idempotency-Key` and return the original response.

### At the first busy week
- **Throughput.** One worker, sequential, measured at **38.9 s a document** sustained — about 92
  an hour, ~66,000 a month flat out. At 100,000 a month, peaks will queue. `fn_claim_document`
  already uses `SKIP LOCKED`, so more workers is a config change; OpenParser's rate limits then
  become the constraint.
- **Queue visibility.** No metric for queue depth, oldest-waiting age, or failure rate.
- **Storage.** `storage/` is local disk. The schema already has `azure_blob_path`; production needs
  Blob Storage — and B12's orphan files fixed first.
- **Pagination.** `limit ≤ 200` + offset, no total. Syncing 100k documents needs cursor paging.

### Before real patient data at scale
- **PHI out of the logs** (B9 — the three leaks found are fixed), and structured JSON logging
  with request ids (not started).
- **Retention and deletion.** No procedure for removing a patient's PHI across database, storage,
  `bench/results` and logs. DPDPA will ask.
- **Data residency.** OpenParser and Anthropic are both in the US. Decision on record from
  2026-09-21; worth revisiting before scale.
- **Backups and restore**, tested.
- **Secrets** from Azure Key Vault, not `.env`.

### Testing that should exist first
- **A two-practice isolation test.** Only one practice has ever existed, so tenant isolation has
  never been tested empirically — only reviewed in code.
- **API tests over HTTP**, and **browser tests that mutate** — both against a disposable database.
- **CI** running the quality gate on every push. Today it runs by hand.
- **A load test** at the target volume.

### B26 · Coverage ignores the code the database stored — and the one a reviewer sets

**High.** Found while fixing B2. Coverage rebuilds each document from its printed labels and
re-matches them against the static dictionary in `ocr/synonyms.py`. It never reads
`lab.results.analyte_id` — the code `fn_resolve_analyte` chose from 578 aliases, or the one a
reviewer set by correction.

- **Measured** over the 291 parsed and verified documents. 653 rows flagged *mapping to confirm*:
  **550 (84%)** carry a stored code identical to the dictionary's guess, 46 a different one,
  57 none. 1,113 *core missing*: **144** are stored on another row of the same document.
- **A reviewer cannot clear a flag.** `fn_correct_result` writes `analyte_id`, which coverage
  never reads.
- **Where the two disagreed, the stored code was right** in every pattern seen — `NON-HDL CHOL.`
  stored as NON_HDL and guessed as HDL; MCH not MCHC; UIBC not TIBC. The screen showed the guess's
  name beside the stored code, inviting a reviewer to "correct" a right record into a wrong one.
  **That display is fixed** (`2891301`); the flags are not.
- **What it does to B2.** Of 288 verified documents the gate would hold 253. Of the 35 it passes,
  **34 are documents where coverage recognised no panel at all** — so as coverage stands, bulk
  confirm confirms what we can check least. The gate is strictly safer than before; it is not yet
  useful.
- **Fix, for decision:** carry the stored code into the rebuilt extraction and count it as an exact
  hit. It changes every coverage chip on the review screen, which is why it was not done quietly.

### B27 · Some core members cannot all be on one report

**Medium.** The commonest *core missing* over the 288 verified documents: `Glucose, Random` in
Blood Glucose (38) and again in Diabetes Profile (38) — every fasting-only report misses it by
construction. Then MPV in CBC (58), Transferrin in Iron Profile (42), Bicarbonate in RFT (40),
Free T3 in Thyroid Profile (37), Fasting Insulin in Diabetes Profile (35).

- Alternatives — fasting or random — cannot both be core, and the others are core but commonly
  unprinted. Each shows red on a report that may be complete.
- **Fix:** a clinical review of the roles in `lab.panel_analytes`. Overlaps with B24.
