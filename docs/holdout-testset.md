# The holdout set — 15 reports the extractor has never seen

Built 2026-09-25. Three invented patients, five reports each, 224 printed
result rows, in
`corpus/data/holdout/` — a separate tree with its own answer key, its own vitals and
its own loader flag.

It exists to answer the question `docs/extraction-benchmark.md` §3 asks and cannot
fully answer: **was the extractor tuned to what we looked at?** `--holdout N` there
splits the same 300 reports by patient number, which controls for *inspection* but
not for *construction* — every one of those 300 uses the same 26 layouts and the same
label spellings the extractor was built against. This set changes both.

---

## What makes it a holdout

| | Training corpus | Holdout |
|---|---|---|
| Patients | P01–P20 | **P21–P23** |
| Reports | 300 | **15** |
| Layouts | 26 | **12, all new** |
| Printed labels | spellings from `catalog.py` | **21 absent from `catalog.py`** |
| Tests with no code at all | 4+ per patient | **9 across the 15** |
| Answer key | `corpus/data/answers/` | `corpus/data/holdout/answers/` |
| Loaded by | `load_corpus.py` | `load_corpus.py --holdout` |
| Patients seeded by | `db/005_…` | `db/019_…`, **skipped by default** |

**The rule that keeps it honest:** none of the unseen spellings may be added to
`catalog.py`. If a label that this set prints gets added to the master because it
failed to resolve, the set stops measuring anything — it has become training data. A
label the master genuinely does not know is *supposed* to come back as an honest blank
in `lab.unmatched_labels`, and measuring how often that happens instead of a confident
wrong code is half the point of the exercise.

Note the one thing this is **not**: it was generated by the same generator, by the
same author, from the same `catalog.py` vocabulary. It is held out from the
*extractor*, which has never been shown it. It is not drawn from a different
distribution, and it is not real lab reports. A genuine out-of-distribution test needs
vendor samples.

## The three patients

| | P21 Prabhakar Deshmukh | P22 Ankita Bhuyan | P23 Thomas Varghese |
|---|---|---|---|
| | M, 54, Nagpur | **F, 11**, Guwahati | M, 41, Kochi |
| UHID | `ORG/451207` | `BRM/730914` | `MRN/558240` |
| Story | Diabetic nephropathy | Iron deficiency anaemia | Alcohol-related hepatitis |
| Tracked | CREAT 1.42 → 3.24 | HGB 7.8 → 12.2 | ALT 186 → 38 |
| Curve | **rising** | rising | **falling** |
| Span | 2024-02 → 2026-04 | 2024-06 → 2026-02 | 2025-01 → 2026-07 |

Three deliberate choices in there:

**P22 is eleven.** Reference intervals are keyed by age and sex, so a haemoglobin of
10.4 is judged against the paediatric band, not an adult one. She is also the only
patient where `EGFR` is correctly absent — CKD-EPI is not valid under eighteen.

**P23 recovers.** Most of the training corpus deteriorates or oscillates. A trend chart
that has only ever rendered a rising line is not proven to render a falling one.

**Three different UHID formats and eight different labels for the UHID field**
(`Hospital No`, `OPD No`, `IP No`, `Member ID`, `Registration No`, `Patient ID`,
`Reg. No`, `UHID`), because UHID detection is the step that decides whether a document
reaches a patient at all.

## The twelve new layouts

Each one breaks a different assumption a line-based parser makes.

| Layout | What it breaks |
|---|---|
| `card_grid` | label sits **above** the value, not beside it — there is no table |
| `sticker_sheet` | peel-off labels, four to a row, with large coordinate gaps between |
| `rtl_columns` | column order reversed: reference, unit, value, **then** the test name |
| `dual_period` | two numbers on every row — this visit and the last, equally bold |
| `newsprint_cols` | three narrow columns, so reading order ≠ text-layer order |
| `form_boxes` | dotted leaders between label and a boxed value field |
| `green_bar` | fanfold stationery, monospace, alternating bands |
| `spine_barcode` | accession text rotated 90° down the left spine |
| `ledger_landscape` | A4 sideways, hairline ruled, very tight leading |
| `grid_lines` | spreadsheet export — every cell boxed, internal lab codes |
| `nabl_ulr` | identifiers buried in an accreditation strip that looks like chrome |
| `pastel_wellness` | status pills instead of H/L, prose reference intervals |

`dual_period` is the one to watch. Both numbers are printed in bold, the previous one
right beside the current one. A parser that takes the first number it finds records the
**old** result and dates it today — a wrong value on the right chart, which is the
failure mode the benchmark already calls the expensive one.

## Running it

```bash
# 1. build it (only needed if corpus/data/holdout/ is missing)
python corpus/generator/build.py --patient holdout --fresh

# 2. seed the three patients - this migration is skipped by default
python scripts/run_migrations.py --with-holdout

# 3. push the 15 PDFs through the real upload path
python scripts/upload_corpus.py --corpus holdout

# 4. score against the sealed holdout key
python scripts/score_corpus.py --corpus holdout --by-layout
```

`--corpus holdout` is not the same flag as `--holdout N`. The first points the scorer
at this tree; the second splits the *training* corpus by patient number and stays what
it was.

To load straight into the database without the API in between:

```bash
python scripts/load_corpus.py --holdout
```

### Skipping step 2 on purpose

Leave `db/019` unapplied and these three UHIDs match no patient, so all 15 documents
land in the review queue with `patient_id` NULL. That is the correct behaviour for a
report belonging to somebody the practice has never registered, and it is worth
measuring on its own — it is the path a real clinic hits on a new referral.

## What to compare against

From `docs/extraction-benchmark.md`, the 2026-09-23 run over the 300:

| Metric | Training corpus |
|---|---|
| Recall | 87.4% |
| Precision | 86.1% |
| Code accuracy | 99.7% |
| Value accuracy | 85.2% |

**Expect the holdout to score worse.** That is the point, and a drop is not a
regression. What the numbers mean:

- **A small drop (a few points)** — the extractor generalises. The layout work was
  structural rather than per-layout tuning.
- **A large drop in recall, concentrated in two or three layouts** — the parser is
  keyed to table shapes it has seen. `--by-layout` names them.
- **A large drop in code accuracy** — the alias resolver is leaning on exact matches
  more than the three-pass funnel suggests. Look at how many unseen spellings landed
  in `lab.unmatched_labels` versus how many got the wrong code. Blanks are fine;
  wrong codes are not.
- **Value accuracy falling further than recall** — check `dual_period` first.

A holdout score close to the training score, on twelve layouts never seen, would be
the single strongest evidence yet that the extractor is doing something real rather
than pattern-matching the corpus it was built alongside.

## Rebuilding

```bash
python corpus/generator/build.py --patient holdout --fresh
python db/seed/export_patients.py --holdout
```

Patient modules are `corpus/generator/patients/p21.py`–`p23.py`, each carrying
`HOLDOUT = True`. That flag is what sends the output to the separate tree and relaxes
the corpus-shape coverage checks — a five-report arc cannot satisfy rules written for
fifteen (each core panel on two or three reports, a tracked analyte on eight). The
rules about a report being *correct* — derived values agreeing with their inputs, ages
advancing, dates ordered, one page unless declared otherwise — still apply in full.
