The job

Indian pathology reports arrive as thermal receipts, carbon copies, faxes, phone photographs and handwriting. They are printed by hundreds of labs that agree on almost nothing.

The same test arrives as Creatinine, Serum, S. CREATININE, Sr.Creat and CREATININE(SERUM). Haemoglobin is measured in g/dL by one lab and g% by another. A platelet count is Lakhs/cumm here and 10⁹/L there. None of it is wrong; none of it is the same.

The system has one job: turn that page into rows a doctor can chart, and be honest about every step where it might have got it wrong.

The rule everything else follows from. A missed row is a hole a reviewer can see. A wrong number is a false reading on the right chart, which nobody sees. So the system prefers an honest blank to a confident guess, and nothing becomes clinical fact until a person has agreed to it.

The pipeline

Seven stages. The first three are the same for every document; the last four are where the system admits what it does not know.

Upload

The file lands through the same endpoint a doctor's browser calls. It is stored, hashed, and queued — nothing is read synchronously, because reading takes seconds to minutes and a request that waits is a request that times out.

POST /documents → lab.documents, status received

Read the page

A worker claims the document and sends it to OpenParser, which returns layout blocks — headers, tables, paragraphs — with coordinates. A digital PDF with a real text layer skips this entirely and is read directly, because rasterising text to ask a model what it says is slower and strictly less accurate than reading the characters already there.

scripts/ocr_worker.py · fn_claim_document

Interpret the blocks

Tables become grids; grids become rows. Which column holds the value, which the unit, which the reference range — none of that is labelled, so it is inferred from what the columns contain. This is where most of the difficulty lives.

app/services/ocr/pipeline.py · columns.py

Resolve the vocabulary

Each printed label is matched against the analyte master through three passes. A label that matches nothing keeps its value and is recorded as unresolved — never dropped, never guessed.

fn_resolve_analyte · fn_resolve_panel

Find the patient

The UHID printed on the page is matched against the practice's patients: exact, then normalised, then fuzzy. A fuzzy match returns a confidence below 1 and the document is quarantined rather than attached. If there is no usable UHID, a demographic match on name, date of birth and sex offers candidates — and can never reach certainty.

fn_match_patient_by_uhid · fn_match_patient_by_demographics

Write the tree

Document, reports, sections, results and notes are written in one transaction. The same file uploaded twice is recognised by checksum and does not duplicate.

fn_ingest_lab_document → status parsed or needs_review

A person agrees

A reviewer sees the page beside what was read from it, corrects any row, and confirms the patient. Only then do the readings become clinical fact. A correction is stored with what the machine had thought, which is how the alias vocabulary grows from real spellings rather than invented ones.

OpenParser, and the raw JSON

OpenParser is a hosted document-layout model. It is given a page and returns blocks: what kind of thing each region is, where it sits, and what it contains.

Tables come back as HTML. That matters more than it sounds — the model has already decided where the cell boundaries are, which is the hardest part of reading a printed table and the part a coordinate-only OCR leaves to you.

Every raw response is kept on disk beside the document. That single decision is why the pipeline can be changed cheaply: a pipeline experiment replays 300 documents from cache in seconds and costs nothing, instead of forty minutes and a bill. Ideas get tried and thrown away, which is not something you do when each measurement is billed per page.

Blocks into rows

A printed table has no schema. Nothing says which column is the result and which is the reference range, and labs disagree about the order. So each column is profiled by what it contains, and the roles are claimed most-distinctive-first.

RoleWhat identifies itWhy it goes in this order
LabelWordy, nearly all distinctClaimed first and leftmost — this stops a serial-number column being read as the result
ReferenceTwo-sided ranges: 13.0 - 17.0The least ambiguous thing on the page, so it goes before the value
UnitMatches a unit lexicon, or its shape—
FlagMostly empty, non-empty cells all markersThe blankness is the signal
ValueBare numbersClaimed last, from what is left

A column that matches nothing convincingly is typed unknown rather than guessed at. Two refinements matter disproportionately, because Indian labs print both constantly: a marker glued to the value (214 H) and a unit glued to the value (12.9 g/dL) are stripped before the numeric test. Without that, a whole panel scores as non-numeric and every reading on it is lost. That second one was problem two.

A printed label becomes a code

The analyte master holds 108 canonical tests. The alias table holds 321 spellings that map onto them. Resolution runs in three passes and reports which one succeeded, so a reviewer always knows how confident to be.

PassMatchesExampleConfidence
1 · exactThe spelling is already knownHaemoglobin1.00
2 · normalisedSame label once case and punctuation stop matteringS. CREATININE → Creatinine, Serum≤ 0.98
3 · fuzzyClose enough, and says how closeT.I.B.C. → TIBCsimilarity

Aliases can be scoped to a practice and to a panel, because the same three letters mean different things in different panels. A label that survives all three passes unmatched is written to lab.unmatched_labels with its value intact.

That table is the most useful thing in the database. It is a ranked list, drawn from real printed pages, of exactly which spelling to teach the system next — currently 361 of them. The vocabulary grows from what labs actually printed, never from what someone imagined they might print.

Every field is stored twice

A result keeps printed_label exactly as the page had it, alongside the analyte_id it resolved to — and, if a human overruled the machine, corrected_from_analyte_id as well. Nothing is overwritten. That is what lets a reviewer see "the page said T.I.B.C., we called it TIBC" and disagree, and what makes a correction evidence rather than an edit.

Panel templates, and the question extraction cannot answer about itself

An extractor knows what it found. It cannot know what it missed. A template says which analytes a named panel should contain, and comparing the two answers that.

Seventeen templates cover the panels Indian clinics actually order — CBC, LFT, KFT, lipid, thyroid, diabetes, iron, coagulation, serology, urine routine and the rest.

missing

The template expects it, the report did not yield it. Either the lab did not run it, or extraction dropped it — and only a missing core member counts against a document.

unexpected

The report yielded an analyte the template does not list. Usually a legitimate add-on; occasionally noise.

unresolved

A printed label matched no canonical code. The vocabulary's gap, not the extractor's. The row keeps its value and is reported as a finding rather than a failure.

Core versus optional is not decoration. Indian labs sell a thyroid panel as T3/T4/TSH or with the free forms added. A flat expected-list would report a perfectly good extraction as a failure on half the market.

The database

PostgreSQL, two schemas, sixteen tables, and roughly two dozen functions. The service owns its own database rather than sharing the EMR's.

Three decisions worth defending

Functions, not ORM-generated SQL. Every write goes through a Postgres function. The validation lives next to the constraint it protects, and the API cannot forget to pass practice_id. Bulk confirmation of 256 documents calls the same function 256 times rather than issuing one UPDATE — so the audit trail and the patient cascade are identical to doing them by hand.

No native enums. VARCHAR with a CHECK, because changing a CHECK is a migration and changing an enum is an outage.

BigInt primary keys, as strings everywhere in the frontend. PostgreSQL BIGINT runs to 263; JavaScript loses integer precision above 253. Parse one into a number and a patient id can change value silently — which in this application means filing a lab report against the wrong person.

One thing that is not enforced. practice_id appears on every table in the lab schema and has no foreign key behind it. Tenancy is upheld entirely by application code — every query filters on the caller's practice. It is deliberate and it is load-bearing, which is a combination worth knowing about rather than discovering.

Two problems, and what they cost

Both were found by measuring, not by reading the code. Both had been quietly wrong for the whole life of the project.

One · A narrow page prints its table sideways

A thermal receipt is too narrow for columns, so labs print label above value — and OpenParser returns that faithfully, one cell per row. The extractor expected columns. It assigned every cell to label, produced rows with no values, and the header pairer — which needs two cells to see a pair — found no patient and no UHID either.

The fix folds the grid into two columns before anything reads it, so nothing downstream needs to know the shape exists. Two header fields, Report Released and Specimen, were also missing from the vocabulary, and one unrecognised key was enough to sink the whole header table.

thermal-slip precision 26.3% → 100.0% UHID recovered on pages that previously yielded none

Two · A unit in the value cell made the value unreadable

Plenty of labs print no unit column and write 12.9 g/dL in the value cell. Column inference asks whether a column holds bare numbers; the unit made the answer no, the column was typed unknown, and every reading on the panel was dropped. The profiler already stripped a trailing flag for exactly this reason, with a comment explaining that not doing so "silently dropped every abnormal panel". Nobody had applied the same reasoning to a trailing unit.

value accuracy 85.2% → 95.6% ≈ 380 readings corrected recall and precision unchanged

Largest single correctness gain in the project. It is also the failure mode the system fears most: those rows were on the right chart, under the right patient, with the wrong number.

The recall targets were missed because the premise behind them was wrong. Folding the grid was expected to recover both the header and the values on narrow pages; it recovers the header. The values on those pages were never the problem — the phantom rows were.

Reporting that is the point. A number nobody can check is worth less than a smaller number somebody can.
