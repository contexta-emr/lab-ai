01

The system

Four processes and three stores. The split that matters: the service answering a browser holds no API keys and no HTTP client, so a compromise there cannot reach a third party or spend money. Only the worker can.

02

Upload — what the browser sends

One multipart request. The server never trusts the filename, the content type or the size — all three are checked before a byte is written to disk.

Request

POST /documents
Authorization: Bearer <jwt>
Content-Type: multipart/form-data

--boundary
Content-Disposition: form-data;
  name="file"; filename="P05-R08.pdf"
Content-Type: application/pdf

%PDF-1.4 …
--boundary--

A single field, file. No practice id, no patient id — both come from the verified token, never from the client.

Checked before anything is stored

extension.pdf .png .jpg .jpeg .webp .tiff .tif
size≤ MAX_UPLOAD_MB, default 25
empty400
duplicatesha256 already seen → the existing row

Rejections are 415, 413 and 400 respectively. A re-upload of the same bytes returns what is already there rather than making a second document, so a doctor pressing the button twice costs nothing.

What lands on disk

storage/025c91e18166bd47_20260923043430.pdf
        └── sha256[:16]  └── UTC timestamp

Named by content, not by what the lab called it. Two uploads of the same bytes collide on purpose; two different files never collide even with identical names.

the original name is kept in core.visit_attachments

What lands in the database

core.visit_attachments gets the file record — original name, stored name, extension, mime type, size, uploader.

lab.documents gets the extraction record with status = 'received', which is what puts it on the worker's queue.

The response is a DocumentSummary with its id as a string — BigInt ids would lose precision above 253 in JavaScript.

03

OpenParser — what we send, and how the PDF travels

The worker claims a document, reads the file back off disk and posts it whole. This is the leg where the entire unredacted PDF leaves India — permitted for this service by decision of 2026-09-21.

The parse call

POST https://api.openparser.dev/parse
Authorization: Bearer <IDP_OPENPARSER_KEY>
Idempotency-Key: <uuid4 hex>
Content-Type: multipart/form-data

part "request"  application/json
part "file"     <the PDF bytes>

Two parts. request is a multipart part with an explicit JSON content type, not a form field — a plain field is rejected.

The request part

{
  "ocr_model": "paddleocr-vl-1.6",
  "output_format": "openparser@1",
  "ocr_options": {
    "image_block_ocr": false,
    "chart_recognition": false,
    "merge_layout_blocks": false
  }
}

The same weights we can run locally, so a comparison measures the hosting rather than a different model. chart_recognition is on by default there and off locally; leaving that difference in would make every comparison an argument about which knob caused it. Lab reports have no charts.

It is a deferred-job API

200result inline, parse it
202a job id — poll GET /jobs/{id} until it finishes
429 · 502 · 503 · 504transient, retried with backoff
4xx otherwiseour bug, never retried

One Idempotency-Key covers the whole logical call. If a 504 leaves the outcome unknown, retrying under the same key returns the result we already paid for instead of parsing — and being billed for — the document a second time.

Refused before upload

A document over 50 MiB is rejected locally. Their admission limit is the same number, and refusing here beats uploading 50 MiB to be told no.

Retail price is $0.001 a page, taken from GET /models/ocr rather than a marketing page. The full 300-document corpus cost about ₹27.

~6 seconds a page · ~20 minutes on paddle_vl locally

What comes back is blocks, not results. A RawDocument of pages, each a list of blocks carrying a label (table, text, doc_title), the recognised content, a bounding box and a reading order. Turning those into rows is a separate problem — the next section.

The three passes, and the escalation

An engine turns pixels into blocks. A pass turns blocks into rows. Two are built, a third is designed and absent — and its absence is why the expensive one fires as often as it does.

PassWhereStatusCostCovers
A — tablespipeline.py · tables.py · columns.pybuilt₹0~92% of documents
B — geometry—does not exist₹0would cluster loose blocks into rows
C — grounded LLMocr/grounded.pybuilt~₹0.06 a docthe 7.7% Pass A returns nothing for
Exactly two places in the package create a Section with rows — pipeline.py and grounded.py. A block Pass A cannot read produces no rows at all; it lands in unparsed_blocks and contributes only header fields. That is why a thermal slip returns zero and falls straight to the pass that costs money.
05

When the key is used, and when it is not

Read once, at worker start, and only with --grounded. Without the flag nothing is read and no third party is contacted. With the flag and no key the worker exits immediately rather than running most of a corpus and skipping quietly.

The key is used

  • the worker was started with --grounded, and
  • a document yielded no rows at all, or a core analyte of a detected panel was not read, and
  • select_blocks found at least one block it is willing to send

23 of 300 documents · one call each

The key is not used

  • the grid readers produced rows and nothing core is missing — 92.3% of documents
  • the flag was not passed, which is the default
  • every block on the page was withheld by the egress control
  • anywhere in the API container, which has neither the key nor an HTTP client

no network call, no cost

A failure to escalate is never a failure. GroundedUnavailableError — no key, no requests, or an API that gave up after its retries — is caught and logged as a skip. The document keeps whatever the grid readers got, which is exactly where it already was.

06

What is withheld, and the rule that is easy to miss

A keyword list alone does not work here, and the reason is worth understanding before anyone edits select_blocks.

Three filters, in order

  • Block label. Only table, table_caption, table_footnote and text can carry a result. Letterhead, page numbers, figures and stamps are dropped unread.
  • Keyword and shape. patient · name · UHID · hospital no · age/sex · referred by · dr. — plus email, mobile, landline and Aadhaar patterns.
  • Follows an identifying block. Whether or not the first was dropped for another reason.

It fails closed

An unrecognised block label is not sent. An unclassified block might be the letterhead, and the control only works if unknown means no.

Reference ranges and collection times are sent — they are payload, not identity, and withholding them would cost rows for nothing.

pinned by tests in test_grounded_selection.py

Why this is permitted at all. The PII design rules out sending the image to an external model — you cannot redact a photograph before you have read it, because finding the name needs the same vision pass you were trying to avoid. This runs after OCR, on text that already exists. And the same document, whole and unredacted, already went to api.openparser.dev one step earlier.
07

Exactly what is passed to the model

Plain Messages API over requests.post. No SDK, no streaming, no tools — the worker already carries an HTTP client for OpenParser and nothing here needs more.

Request

POST https://api.anthropic.com/v1/messages
x-api-key: <ANTHROPIC_API_KEY>
anthropic-version: 2023-06-01
content-type: application/json

{
  "model": "claude-haiku-4-5-20251001",
  "max_tokens": 2048,
  "system": "<reading instructions>",
  "messages": [
    { "role": "user",
      "content": "<the blocks>" }
  ]
}

The blocks, verbatim

b0 @1:30,62,250,70    Accession No.
b1 @1:30,71,237,80    MCH23-047304
b2 @1:30,105,302,112  Sample Collected
b3 @1:30,114,338,123  16/09/2023 8:20 AM
b5 @1:30,189,171,198  Specimen
b6 @1:30,199,333,208  whole blood (EDTA)
b7 @1:30,232,197,242  Plt Count
b8 @1:742,243,963,253 96000 /uL L

ref · page · box as integers 0–999 · then the text, untouched. Position is most of what separates a label from its value on a page with no table structure — the one signal the grid readers could not use, because there was no grid to use it in.

Response

LABEL_REF | VALUE_REF | LABEL | VALUE | UNIT | FLAG

b7 | b8 | Plt Count | 96000 | /uL | L

Two refs, not one. On a till roll the label and the value are always separate blocks — demanding both in one block rejected correct readings for being correctly attributed, which is the bug the first live call found.

Not JSON mode

Constrained decoding costs 3–9 points of accuracy across open-weight models, and one benchmark saw output validity fall from 51% to 37% under structured output.

A malformed line is simply not a row. The guarantee is the grounding check, not the schema.

~430 tokens in, ~20 out, a document

08

The grounding check

A row survives only when both cited blocks were actually sent, the label appears in the label's block, and the value appears in the value's block. Each half is proved against its own block.

If the model…Caught by
invents a value outrightit appears in no block
invents a value inside a real blocknot in the block it cites
borrows another test's numbernot in the block it cites
invents a block idb9 was never sent
attaches a label to the wrong blocknot in the block it cites

Refs are indices into what we sent, not engine ids — so a model citing b9 when nine blocks went fails the check rather than landing on something real by accident. Rejected rows carry a reject key naming the test they failed, because the rejection rate is the measurement that says whether this pass is earning its money.

09

The database

Two schemas. lab is ours; core is a compatibility subset shaped like the EMR's, so this ports without changing a table there. Every write to lab.* goes through a function — the API never inserts directly.

Why functions, not INSERTs

One code path by which a document becomes clinical fact. Alias resolution, panel detection and UHID matching all happen inside fn_ingest_lab_document, so a fixture loaded by a script exercises exactly what production does.

lab.v_results_verified is the only view a clinical read should touch

Conventions carried from the EMR

  • BigInt identity keys, crossing the wire as strings
  • practice_id on every tenant-scoped table, from the token, never from the client
  • No native enums — VARCHAR + CHECK, because changing a CHECK is a migration and changing an enum is an outage
  • TIMESTAMP(6), explicit lengths, snake_case
